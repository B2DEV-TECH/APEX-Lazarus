# APEX Lazarus — MVP Specification

Version 0.2 · 2026-11-10 · Geraldo Viana Jr

## Thesis

Lazarus turns a production error into a validated merge request, with a person deciding whether it ships. It never changes production on its own.

The problem: hours pass between a user seeing ORA-01403 and a developer opening the right page in App Builder, and most of that time goes into reproducing the error, not fixing it. Lazarus automates that part: it captures the context, reproduces the failure in isolation, proposes a fix and shows evidence that the fix works.

What the project demonstrates, with reproducible evidence:

- An agent can fix a bounded class of APEX errors with no write access to production.
- Every patch is a readable APEXlang diff, reviewable like any merge request.
- When a fix is outside those bounds, Lazarus refuses and records why instead of trying.

Positioning: trustworthy agent engineering applied to APEX. The project is about the agent's limits more than its autonomy.

## MVP scope

### In scope

- One APEX 26.2 application, exported as APEXlang and versioned in Git. Git is the single source of truth for the application.
- Three error classes whose fix lives in a page definition:
  - ORA-01403 / ORA-01422 in page processes and computations (unhandled no-data-found, too-many-rows).
  - ORA-00904 in region sources after a column was **renamed**. A dropped column is refused: removing it from the page changes what users see, which is a product decision.
  - ORA-06502 in validations and computations (conversion and length errors).
- Capture through the application's error handling function, or through one call added to an existing one.
- Reproduction on a development instance, outside the page engine, on demo data that is reset before every attempt.
- A patch that changes exactly one `.apx` page file, validated with SQLcl and imported into the development copy of the application with file-level import.
- Review through an APEX Human Task that shows the diff and the evidence. Approval opens a merge request. **Merging the merge request is the gate to deployment.**
- Promotion to production only through the team's normal full-application deployment from Git.

### Out of scope

- Any write to production by Lazarus. Oracle states that file-level import, although it may technically work in production, is intended primarily for development and testing.
- Shared components, themes, templates, plug-ins and workspace components.
- DDL, data fixes, and changes to PL/SQL packages (candidate for v2).
- Patches that span more than one file, add or remove components, or change properties outside the allow-list (see Guardrails).
- Errors raised by APEX internals or by external systems (REST sources, EBS).

### Definition of done

- A public repository (UPL-1.0) with an install script, a demo application and a seeded fault set: 15 in-scope faults (5 per error class) and 5 out-of-scope decoys whose correct outcome is a refusal.
- A results table generated by a script anyone can rerun, in two modes: replay (recorded model responses, no model key needed) and live.
- A written limits section: what Lazarus refused, what it failed to fix, and what it got wrong.

## Architecture and flow

Lazarus has three zones with one-way traffic:

1. **Production only emits incidents.** The capture handler inserts into one table, `LZ_INBOX`.
2. **All repair work happens on a development instance.** An intake job there pulls new inbox rows through an account that can only `SELECT` from `LZ_INBOX`.
3. **Nothing returns to production except through a person and the normal pipeline**: a merged merge request, deployed from Git.

An incident leaves the development zone in one of three ways: as a validated patch for review, as a refusal with a recorded reason, or as a failure after the attempt budget is spent. A reviewer who rejects the patch closes the incident.

The public demo runs both environments on one host, as separate pluggable databases with their own APEX installations. If a setup shares one APEX instance between them, the application IDs collide and the import must target another ID (see Risks).

## Data model

### Production (LAZARUS schema)

| Table | One row per | Notes |
|---|---|---|
| `LZ_CONFIG` | One row | Capture switch and the HMAC key for user names. Not readable by the pull account. |
| `LZ_INBOX` | Captured occurrence | Insert-only from the handler: app, app version, page, component type, ID and name, `ora_sqlcode`, `ora_sqlerrm`, error statement, backtrace, user HMAC, session state (JSON, raw values), captured at. |

### Development (LAZARUS schema)

| Table | One row per | Key columns |
|---|---|---|
| `LZ_INCIDENT` | Distinct error (deduplicated) | fingerprint, app_id, app_version, page_id, component_type, component_id, component_name, error_code (normalized), error_statement, error_backtrace, occurrences, first_seen, last_seen, status, recurrence_of |
| `LZ_CONTEXT` | Occurrence pulled from the inbox | incident_id, source_inbox_id, app_user_hmac, session_state (raw, JSON), captured_at, purge_after, purged_at |
| `LZ_ATTEMPT` | Repair attempt | incident_id, attempt_no, guard_verdict, refusal_reason, repro_result, model, temperature, tokens_in, tokens_out, started_at, finished_at |
| `LZ_PATCH` | Proposed patch | attempt_id, file_path, diff, scan_result, validate_result, import_result, rerun_result, regression_result, evidence (JSON), branch, merge_request_url |
| `LZ_AUDIT` | State transition | incident_id, from_status, to_status, actor_type (agent, runner, person, system), actor, changed_at, note |

- **Fingerprint**: a hash of app, page, component ID and normalized error code, so 500 occurrences of one bug produce one incident. `ora_sqlcode` carries the SQLCODE, and NO_DATA_FOUND arrives as `+100`, so the intake maps `100` to `ORA-01403` and every other code to `ORA-nnnnn`. Two failing statements in the same component with the same code also collapse into one incident; this is a known MVP limitation.
- **Status**: `NEW` → `REFUSED` or `REPRODUCED` → `PATCHED` → `VALIDATED` → `IN_REVIEW` → `APPROVED` (merge request opened) or `REJECTED`; `APPROVED` → `MERGED`. `FAILED` when the attempt budget is spent without a validated patch. A fingerprint that occurs again after `MERGED` opens a new incident linked through `recurrence_of`.
- **Raw values and retention**: session-state values are captured raw, because the three error classes depend on them (a missing key, a value too long, text where a number is expected). They exist in two places, both restricted to the LAZARUS owner and the pull account:
  - `LZ_INBOX` in production: deleted after 7 days by a scheduler job owned by LAZARUS. This purge is the only change to production data other than the handler's inserts, and it stays inside production.
  - `LZ_CONTEXT` in development: values are cleared when the incident closes, and in any case after 14 days. The row is kept with `purged_at` set.
  - Raw values never reach the model (see Guardrails).
- `LZ_AUDIT` is insert-only, enforced by a trigger. An immutable or blockchain table is a natural upgrade and stays out of the MVP.

## Components

Lazarus is six PL/SQL packages plus one external runner. The runner exists because file-level import is available only through SQLcl and the SQL Developer extension for VS Code, not from inside the database or App Builder.

| Component | Runs in | Responsibility |
|---|---|---|
| `LZ_CAPTURE` | Production | `handle`: error handling function. `log_incident`: one call for applications that already have a handler. Inserts into `LZ_INBOX` in an autonomous transaction, never raises, and never changes what the user sees. |
| `LZ_INTAKE` | Development | Pulls new inbox rows, normalizes error codes, deduplicates into `LZ_INCIDENT` and `LZ_CONTEXT`, purges expired values. |
| `LZ_GUARD` | Development | Decides whether an incident is in scope, before the agent runs and again on its patch. Returns a verdict and a reason. |
| `LZ_REPRO` | Development | Re-executes the failing component with the captured context, outside the page engine. |
| `LZ_AGENT` | Development | Builds the prompt (error, page file, masked context, reproduction result) and stores the proposed file. |
| `LZ_REVIEW` | Development | Creates the Human Task and records the decision. |
| Runner (shell or Python) | CI host | Git checkout, reset the development application, write the patched file, validate, file-level import, trigger re-run and regression check, push the branch, open the merge request. |

### Capture

`LZ_CAPTURE` is deliberately small, because it is the only Lazarus code that runs in production (`db/prod/02_lz_capture.pkb`).

An application has one error handling function:

- An application without one sets it to `lazarus.lz_capture.handle`.
- An application that already has one adds a single call to `lazarus.lz_capture.log_incident(p_error)` inside it, so its users keep seeing the messages that handler produces.

### Reproduction

`LZ_REPRO` does not run the page through the APEX engine. The engine commits at the end of page processing, and page code can commit, use autonomous transactions or call external systems. A savepoint cannot undo any of that.

- **Region source (ORA-00904)**: parse the region's SQL with `DBMS_SQL`. An invalid identifier fails at parse time, so nothing is executed.
- **Process, computation or validation**: create an APEX session for the application and page (`APEX_SESSION.CREATE_SESSION`), set the captured item values, and run the component's PL/SQL with `APEX_EXEC.EXECUTE_PLSQL`, which binds page items automatically. This runs inside a savepoint that is always rolled back.
- **Before each attempt**, a script resets the demo data, so a side effect that escapes the rollback cannot leak into the next run.
- **`LZ_GUARD` refuses components** whose code contains `COMMIT`, `ROLLBACK`, `PRAGMA AUTONOMOUS_TRANSACTION`, DDL, `UTL_*`, `APEX_WEB_SERVICE`, `APEX_MAIL` or `DBMS_SCHEDULER`.

Running a component outside the engine is not identical to running the page. The benchmark measures how many seeded faults still reproduce this way.

### Patch path

1. Reset the development application from Git HEAD (full import).
2. Write the patched `.apx` page file.
3. Validate the whole application directory offline: `apex validate -input <app-dir>`.
4. Import only the patched file, from the parent of the application directory, connected to the application's parsing schema (which must be REST-enabled):

   ```
   apex import -input my-app/ -files my-app/pages/p00003-employees.apx
   ```

5. Re-run the reproduction and the regression check against the development application.
6. On a validated patch, push a branch and create the Human Task.

### Review

- The Human Task shows the APEXlang diff, the reproduction before and after, the regression result and the scan result.
- **Approve**: the runner opens the merge request, with the evidence in its description.
- **Reject**: the incident moves to `REJECTED`.
- **Merge**: merging the merge request is the gate to deployment, which runs through the team's normal pipeline from Git. The development application is never promoted.

## Guardrails

Lazarus is fail-closed: when a rule below is not clearly satisfied, the incident is refused with a recorded reason, and a person takes over.

| Rule | Why |
|---|---|
| The agent's database user has no grants on production. The only cross-zone account is the pull account, with `SELECT` on `LZ_INBOX` only. | The strongest guarantee is the one the database enforces. |
| A patch changes exactly one page `.apx` file, modifies existing components only, and changes only allow-listed properties: the SQL source of a region and its columns (ORA-00904), the PL/SQL code of processes, computations and validations, and error messages. Any other changed property, or an added or removed component, is refused. | An allow-list fails closed. A list of forbidden security attributes misses some, such as escaping, server-side conditions and build options. |
| A static scan refuses patches that contain `COMMIT`, `ROLLBACK`, DDL, `EXECUTE IMMEDIATE`, `DBMS_SQL`, `UTL_*`, `APEX_WEB_SERVICE`, `APEX_MAIL`, `GRANT`, `PRAGMA AUTONOMOUS_TRANSACTION`, or `WHEN OTHERS` without a `RAISE`. | The model's code runs on the development instance, and the prompt contains untrusted input. |
| The development parsing schema has no network ACL and no system privileges. | Limits what an injected instruction could do. |
| The incident's application version must match the version in Git HEAD. For ORA-00904, the development schema must have received the same DDL as production. | A fix made against a different version proves nothing. |
| The error must reproduce before the agent is called. | No reproduction means no way to prove a fix. |
| The patched page must pass the reproduction and the regression check for its fault. | Guards against fixes that hide the error instead of removing it. |
| At most two attempts per incident, with a token budget per attempt. | Bounded cost and no retry loops. |
| The model receives item names, data types, lengths and shape-preserving masks, never raw values. Raw values stay in `LZ_CONTEXT` until purged. | Session state can contain personal data. |
| Error text and row data are untrusted input in the prompt. The model's output is untrusted too: the runner never uses it as a branch name, file path or command argument without validation. | An error message or a stored value can carry a prompt injection. |
| A person approves every patch in the Human Task, and a person merges every merge request. | Lazarus proposes; it does not decide. |
| Two switches: capture (`LZ_CONFIG` in production) and the runner (development). | With one-way traffic, production cannot read a switch kept in development. |

Refusals are a feature of the results, not a failure to hide: the refusal counts and their reasons are published next to the fix counts.

## Regression oracle

Each seeded fault is made by breaking a page that worked. The working version is the oracle: for each fault, the fault set stores inputs and the expected outcome taken from the working version, such as the rows the region returns, the item values after processing, or the validation message the user should get. The regression check runs those inputs on the patched page and compares.

What counts as fixed, per class:

- **ORA-01403**: the missing row is handled the way the expected outcome says (a value or a message), not skipped silently.
- **ORA-01422**: the query returns the row the expected outcome identifies. Restricting the query to an arbitrary row (`ROWNUM = 1`, or `FETCH FIRST` without an `ORDER BY` that identifies the row) fails.
- **ORA-00904**: the region returns the same rows and columns as the working version, using the renamed column.
- **ORA-06502**: the value is converted correctly, or the user gets the expected validation message.

## Benchmark and metrics

- **Fault set**: 15 in-scope faults (5 per class) and 5 decoys whose correct outcome is a refusal, for example a dropped column, a fix that needs a shared LOV, a fix that needs an authorization change, an error raised in package code, and an error that no longer reproduces because the data changed.
- **Repetitions**: the model and temperature are fixed and recorded. Each fault runs N times (default 3), and every run is published.
- **Results**, as counts and percentages:
  - In-scope faults: fixed, failed, refused (a false refusal). The three add up to 15 per run.
  - Decoys: refused with the expected reason, refused with another reason, not refused.
  - Wrong-fix attempts: patches that passed the reproduction and failed the regression check.
  - Median machine time from error to `VALIDATED`. Human time from `IN_REVIEW` to the decision is reported separately.
  - Tokens per incident.
- **Replay mode**: model responses are recorded by prompt hash, so anyone with APEX 26.2 and SQLcl 26.2 can rerun the pipeline without a model key. Live mode needs a key.

## Demo script

The demo breaks a page live and ends with a merge request nobody typed, in under ten minutes of screen time.

1. Show the demo app working: an employee form that saves.
2. Break it on camera: rename a column the page's region source selects. The same DDL runs on the development database as part of the scripted deployment.
3. Open the page as a user. The error appears; nothing else happens on screen.
4. Switch to the Lazarus console: one new incident, with page, component, ORA-00904 and occurrence count.
5. Watch the incident move through `REPRODUCED`, `PATCHED` and `VALIDATED`.
6. Open the Human Task: the APEXlang diff on the left; the reproduction before and after and the regression result on the right.
7. Approve. Show the merge request that was opened, with the evidence in its description. Merging it is the deployment gate.
8. Drop a column instead. Lazarus refuses: the fix would change what users see. Show the refusal reason. This is the most important minute of the demo.

## Four-week plan

Week 1 is a proof of concept that can kill the project early; the agent is not written until the mechanical loop works by hand.

| Week | Build | Exit check |
|---|---|---|
| 1 | Demo app, `LZ_CAPTURE`, inbox and development tables, `LZ_INTAKE`. By hand: edit one `.apx` page file, validate, file-import into the development application. Confirm on the instance: the `-files` syntax (`help apex import`), the reset-then-import sequence, `APEX_HUMAN_TASK` in 26.2, and that each error class reaches the handler with `component` filled, region rendering errors included. | A hand-written patch fixes a seeded ORA-00904 through the full mechanical path. |
| 2 | `LZ_REPRO`, `LZ_GUARD`, the runner, the data reset, the 15 faults and 5 decoys with their oracles. | Every in-scope fault reproduces and every decoy is refused, with no agent involved yet. |
| 3 | `LZ_AGENT`, static scan, allow-list diff check, regression check, attempt and token limits, replay recording. | The first full benchmark run produces the results table. |
| 4 | Human Task review page, merge request integration, README, limits section, recorded demo. | A stranger can clone the repository and rerun the benchmark in replay mode. |

If week 1 fails, the cause is most likely how file-level import behaves on the instance, and that finding is itself worth an article.

## Risks and open questions

The largest risk is reproduction fidelity, not the model: if Lazarus cannot rebuild the failing state, nothing downstream matters.

| Risk | What is not yet known | How it is answered |
|---|---|---|
| Reproduction fidelity | Running a component outside the engine differs from running the page, and some failures depend on data that changed since capture. | Count how many of the 15 faults reproduce from the captured context alone. |
| Handler coverage | Whether all three classes, in every component type, reach the error handling function with `component` filled. | Week 1. |
| Import target | Whether the import can target another application ID when one APEX instance hosts both environments. | Week 1. The demo default is two pluggable databases, which avoids it. |
| File-level import dependencies | With several files, SQLcl resolves the order among them. How it behaves when the page references a component that changed and is not in the import is untested. | One page file per patch; refuse fixes that need a new or changed shared component. |
| Model quality on APEXlang | No measured data on how often a model produces a valid `.apx` page file for these classes. | The benchmark is the measurement. Validation failures count as failed attempts. |
| Raw values on development | Personal data on the development instance. | Retention limits, restricted access, masking before the prompt, and synthetic data in the public demo. |

## Revision notes (0.1 → 0.2)

- Reproduction runs outside the page engine and on reset data. A savepoint alone does not undo the engine's commit or the page code's side effects.
- Raw session-state values are captured for reproduction, with retention limits; only masked values reach the model.
- Production holds one insert-only table, `LZ_INBOX`. Deduplication and `LZ_CONTEXT` moved to development, which pulls the inbox with a `SELECT`-only account.
- A regression oracle per seeded fault, taken from the working page.
- Patches are applied to the development application, reset from Git before each attempt, instead of an App Builder Working Copy. Git is the single source of truth.
- Security rules for patches are an allow-list of properties, plus a static scan of the patched code.
- `log_incident` lets an application keep its existing error handling function.
- `ora_sqlcode` normalization (`+100` is ORA-01403).
- Metrics: failed attempts are counted apart from refusals, 5 decoys measure correct refusals, runs are repeated, machine time is reported apart from human time, and a replay mode allows reruns without a model key.
- Version check between the incident and Git HEAD. A dropped column is refused, and that refusal is the demo's refusal case.
- Statuses `FAILED` and `MERGED`, plus recurrence after a merge. User names are stored as an HMAC. There are two kill switches.
